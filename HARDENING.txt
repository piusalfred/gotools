  What Go Already Handles (Don't Reinvent)

  First, let's be clear about what's already cached by the Go toolchain so we don't build things Go gives us for free:

  ┌───────────────┬────────────────────────────────────────────────────────────────┬─────────────────────────────────────────────┐
  │     Layer     │                         What Go caches                         │                    Where                    │
  ├───────────────┼────────────────────────────────────────────────────────────────┼─────────────────────────────────────────────┤
  │ Module cache  │ Downloaded module zip files                                    │ GOMODCACHE (default ~/go/pkg/mod)           │
  ├───────────────┼────────────────────────────────────────────────────────────────┼─────────────────────────────────────────────┤
  │ Build cache   │ Compiled binaries                                              │ GOCACHE (default ~/Library/Caches/go-build) │
  ├───────────────┼────────────────────────────────────────────────────────────────┼─────────────────────────────────────────────┤
  │ Tool binaries │ go tool <name> looks up compiled binaries from the build cache │ Same build cache                            │
  └───────────────┴────────────────────────────────────────────────────────────────┴─────────────────────────────────────────────┘

  So when gotools sync runs go mod tidy + go get -tool and the versions haven't changed, Go itself doesn't re-download or recompile — it hits its own caches.
  That's the good news.

  The bad news is that gotools never exploits this knowledge. Every sync still spawns N go processes, does the temp-dir dance for split strategy, copies files
  around, and cross-checks things — even when nothing changed.

  ---
  The Real Gaps for CI at Scale

  🔴 Gap 1: No fast-path for "nothing changed" (Highest Impact)

  This is the single biggest win. Look at cmd_sync (lines 1298–1374): it unconditionally runs go mod tidy on every single modfile, every time. For split
  strategy, that means per-tool temp dir creation + file copies + replace edits.

  In a monorepo with 20 tools and 1000 PRs/day on CI, you're running 20,000 tidy operations per day that all do nothing useful.

  What should happen: Before the tidy phase, compare the manifest's state hash (or a checksum of the modfile contents + go version) against a stored
  fingerprint. If nothing changed, skip the entire tidy phase. This makes the common case (CI run where no tooling changed) a ~5ms no-op.

  Implementation sketch:
  # In sync: compute a fingerprint of the manifest tool list + go version
  _fingerprint=$(echo "$_MANIFEST_TOOLS" | md5sum)
  _fingerprint+="|$target_v"
  if [[ -f "$GOTOOLS_DIR/.gotools.fingerprint" ]] && \
     [[ "$(cat "$GOTOOLS_DIR/.gotools.fingerprint")" == "$_fingerprint" ]]; then
      # Everything matches — skip tidy entirely
      echo "✅ Tools up to date (cached)."
      return 0
  fi
  # ... do the tidy work ...
  # After success:
  echo "$_fingerprint" > "$GOTOOLS_DIR/.gotools.fingerprint"

  🔴 Gap 2: No version-aware skip during sync

  Lines 1404–1408: sync's reinstall check is existence-only. If tools/gofumpt.mod exists on disk, sync assumes the tool is fine — it never checks whether the
  version in the modfile matches what the manifest says.

  This means if someone force-upgrades a tool but the manifest doesn't get flushed (crash, partial failure), sync won't detect the mismatch next time.

  What should happen: Read the installed version from the modfile's require block and compare it to the manifest. If they match, skip. If they don't,
  reinstall at the manifest's pinned version.

  🟡 Gap 3: No binary-existence fast check

  cmd_install runs go get -tool (which modifies the modfile, potentially hits network) and then verifies the binary via go tool <binary> </dev/null>. But if
  the binary is already compiled in Go's build cache (e.g., from a prior CI run), and the version in the modfile matches, you could skip the go get -tool call
  entirely.

  What should happen: Before go get -tool, run go tool <binary> </dev/null> to check if the binary is already cached and runnable. If yes, verify the version
  matches, and skip the network round-trip.

  🟡 Gap 4: No offline/frozen mode

  For CI reproducibility, you want a mode that says: "Use exactly what's pinned. If anything requires network, fail."

  There's currently no GOTOOLS_OFFLINE=1 or --frozen flag. The script always lets go get -tool hit the network if the module cache is cold.

  What should happen: A GOTOOLS_OFFLINE=1 env var (or --offline flag) that sets GOFLAGS=-mod=readonly and GOPROXY=off (or
  file://${GOMODCACHE}/cache/download), combined with the fast-path check from Gap 1. If the fingerprint matches, exit immediately. If it doesn't, fail with a
  clear message telling the user to run gotools sync locally.

  🟡 Gap 5: Lock contention in CI matrix builds

  The lock (lines 92–108) uses a 10-second hard timeout with 0.5s polling. In CI, when you have a matrix of 5 Go versions × 3 OSes all hitting the same
  workspace (e.g., via a shared volume), you get spurious failures.

  What should happen: A GOTOOLS_NO_LOCK=1 env var for CI environments where you know there's no real concurrency, or a GOTOOLS_LOCK_TIMEOUT env var to let CI
  increase the timeout. Better yet, in --frozen/offline mode, skip the lock entirely since you're only reading.

  🟢 Gap 6: Trace log growth

  The .gotools_trace.log (line 1655) is append-only with no rotation. In CI with thousands of runs, this file grows without bound.

  What should happen: A max-size check at trace-write time. If the log exceeds, say, 1MB, rotate it (.gotools_trace.log.1). Or, since CI ephemeral workers
  don't care, make this configurable: GOTOOLS_TRACE_MAX_SIZE.

  🟢 Gap 7: No GOMODCACHE sharing strategy

  The script never sets GOMODCACHE, but in CI, pointing GOMODCACHE at a persistent/shared location turns cold starts into warm starts. This isn't something
  gotools needs to implement, but it should be documented — show CI configs that mount a persistent module cache volume.

  🟢 Gap 8: No install timeout

  A single go get -tool that hangs (network issue, proxy down) blocks the entire lock for the full 10-second timeout plus however long Go takes to give up.
  There's no per-tool timeout.

  Building a CLI tool manager for CI/CD and massive concurrency is vastly different from writing a local installation script. When a tool is executed thousands of times per minute across ephemeral CI runners, naive download strategies will immediately fail due to network rate limits, race conditions, and heavy process overhead.

  Here is the comprehensive, production-grade hardening checklist for building a highly concurrent Go tool manager.

  ## 1. Performance & Execution (The Concurrency Standard)

  At CI scale, network I/O and process spawning are your primary bottlenecks.

  * **Lazy Execution (Shims):** Do not download all tools upfront during a setup step. Instead, generate lightweight proxy executables (shims) that intercept commands (e.g., `golangci-lint`), check if the binary is cached, and install it just-in-time only if it is actually invoked.
  * **Atomic File Operations:** In CI matrices, multiple parallel jobs will attempt to download and install the exact same tool simultaneously. Prevent corrupted binaries by downloading payloads to a temporary file (`uuid.tmp`) and using atomic operations (like `os.Rename`) to move them into the final cache path.
  * **Zero-Overhead Process Replacement:** Shims must intercept every call. To prevent dangling file descriptors and exhausting process ID limits, write shims in Go and use `syscall.Exec`. This replaces the shim's process with the target binary natively, rather than spawning a heavy child process.
  * **Hierarchical Caching Strategy:**
  * *L1 (Project Local):* In-project symlinks pointing to the global cache.
  * *L2 (Global Cache):* A shared `$XDG_DATA_HOME` or `$HOME/.yourtool` registry to prevent re-downloading the same binary across different projects on the same machine.
  * *L3 (Network Proxy):* Support resolving modules via `GOPROXY` or an internal artifact CDN to ensure high availability and bypass GitHub API rate limits.



  ## 2. Security & Supply Chain Hardening

  A centralized tool manager that automatically downloads and executes third-party code is a prime target for supply-chain attacks. You must treat all external binaries as untrusted.

  * **Mandatory Checksum Verification:** Never execute a downloaded payload without verifying its SHA-256 or SHA-512 checksum against a locked, declarative manifest. If the checksum does not match, the manager must fail closed and delete the payload immediately.
  * **Provenance Verification:** Support Cosign signature verification and SLSA provenance out of the box. This guarantees the binary was securely built by the official maintainer's pipeline, rather than manually uploaded by a compromised maintainer account.
  * **Disable CGO (If building from source):** If your manager falls back to compiling tools from source, strictly enforce `CGO_ENABLED=0`. C dependencies bypass Go's native memory safety guarantees and blind vulnerability scanners like `govulncheck`.
  * **Distroless Defaults:** If you provide official container images for your tool manager, package them using scratch or distroless base images to minimize the attack surface strictly to your code and the Go runtime.

  ## 3. Configuration & Interoperability

  Your tool must blend seamlessly into any OS, shell, and CI system without developer friction.

  * **Declarative Version Pinning:** Manage tool versions via a unified YAML manifest (e.g., `tools.yaml`). This forces teams to pin exact versions strictly, completely eliminating "works on my machine" drift.
  * **Context-Aware Isolation:** The manager must dynamically switch tool versions based on the current working directory. This allows developers to seamlessly hop between a legacy project requiring `mockgen v1.4` and a modern one requiring `v1.6`.
  * **OS/Arch Native Mapping Engine:** GitHub release naming conventions are famously chaotic. Build a robust internal mapping engine that translates standard Go environment variables (`GOOS`/`GOARCH`) to match wild release artifacts (e.g., dynamically resolving `darwin/arm64` to `macOS_AppleSilicon.tar.gz`).
  * **First-Class CI Integrations:** Provide out-of-the-box GitHub Actions (e.g., `setup-yourtool`) and GitLab CI components that automatically hash the `tools.yaml` file to securely cache and restore the `$XDG_DATA_HOME` directory.

  ---

  > **Key insight:** The hallmark of a high-performance tool manager is invisibility. During a "happy path" cache hit, the entire verification and execution lifecycle should introduce less than 5 milliseconds of overhead.

  ## 4. Developer Experience (DX)

  * **Zero-Dependency Distribution:** Ship the manager itself as a single, statically linked binary. It must be installable via a simple `curl` command onto a pristine CI runner without requiring Node.js, Python, or external system libraries.
  * **Interactive Discovery:** Include a built-in TUI (Terminal User Interface) fuzzy-finder so developers can search the registry and install tools interactively without needing to look up the exact repository name in a browser.
  * **Dependabot/Renovate Native:** Structure your YAML configuration cleanly so that automated dependency management bots can natively parse it, verify the registry, and open automated PRs when linters or formatters release new versions.
